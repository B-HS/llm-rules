# AI PROCESS — AI 작업 프로세스

> AI 코딩 에이전트가 이 저장소 및 이를 참조하는 프로젝트에서 작업할 때 **무조건 따라야 하는 운영 규칙**이다.
> Codex 환경에서는 이 문서가 **`AGENTS.md`의 참조 프로토콜**을 통해 매 작업에 적용된다.
> [common.md](./common.md) · [comments.md](./comments.md) 등 코딩 컨벤션은 "코드가 어떻게 생겨야 하는가"를, 이 문서는 "AI 가 어떻게 일해야 하는가"를 규정한다.

---

## 0. 적용 방식

- Codex 사용 시, 프로젝트 또는 글로벌 `AGENTS.md`가 이 문서의 위치를 참조하도록 명시한다.
- **다른 코딩 에이전트(Claude Code · Cursor · Copilot · Windsurf 등)** 는 각 에이전트의 룰 파일(`CLAUDE.md` · `.cursor/rules` 등)에서 이 컨벤션 묶음을 **명시적으로 로드/참조**하도록 설정한다.
- 이 규칙은 **선택이 아니라 절대**다. 모든 요청·세션에서 항상 우선한다.

### 0.1 커뮤니케이션 (원칙 17)

> **항상 간결하게, 존댓말로 답한다.**

모든 응답·문서·커뮤니케이션은 **한국어 + 존댓말**로 작성하고, 아래 실행 계약을 따른다. ([common.md](./common.md) §1)

1. **첫 줄에는 바로 실행할 행동이나 직접적인 정답을 쓴다.** 배경·계획 예고·서론부터 시작하지 않는다. 명령어·경로·코드 조각이 답이면 그것을 먼저 제시한다.
2. **두 단계 이상인 작업은 번호 목록으로 쓴다.** 각 단계에는 명확한 행동 하나만 두고, 완료에 필요하지 않은 단계는 제거하거나 가까운 단계에 합친다.
3. **남은 작업이 있으면 2분 안에 실행할 수 있는 구체적인 다음 행동 하나로 끝낸다.** 남은 작업이 없으면 완료된 결과로 끝내며, 인사·추가 도움 제안·반복 요약을 붙이지 않는다.
4. **현재 요청과 직접 관계없는 곁가지를 억제한다.** 작업 중 생긴 관련 판단은 스스로 해결하고, 사용자 결정이 꼭 필요하면 현재 작업의 결정만 마지막에 한 번 묻는다. 별도 문제는 현재 문제를 끝낸 뒤 다음 작업 후보로만 제안한다.
5. **매 응답에서 현재 상태를 한 줄로 다시 명시한다.** 여러 단계의 작업은 표시상 상위 단계 하나만 진행 중으로 두되, 그 단계 아래의 독립 하위 작업은 실제로 병렬 실행할 수 있다. 체크리스트나 작업 도구가 있으면 같은 상태를 중복 서술하지 않는다.
6. **관찰 가능한 근거가 있을 때만 구체적인 시간 단위로 예상한다.** 근거가 없거나 외부 대기처럼 변동 폭이 크면 시간을 만들지 말고, 다음 상태를 알릴 조건을 제시한다.
7. **완료 결과를 눈에 보이게 제시한다.** 현재 작동하는 기능, 실행 명령, 경로, 테스트 결과처럼 사용자가 직접 확인할 수 있는 사실을 앞에 둔다.
8. **오류는 원인·관찰값·해결 또는 다음 진단을 담담하게 쓴다.** 감탄사나 근거 없는 불확실성 표현을 넣지 않는다.
9. **최종 응답의 화면상 목록은 관련 항목을 묶어 그룹당 5개 이하로 표시한다.** 완전성이 필요한 정보는 내부적으로 유지하고, 생략하면 안 되는 항목은 여러 작은 그룹으로 나눈다.
10. **서론·완료 내용의 반복 요약·마무리 인사를 쓰지 않는다.** 미사여구·과장·빈말·관용적 비유를 제거하고, 결론과 필요한 근거만 남긴다.

다음 상황에서는 안전과 작업 성립을 위해 위 형식을 필요한 만큼 조정한다.

1. 사용자가 설명이나 단계별 과정을 요청하면 필요한 만큼 자세히 쓰되 서론·마무리 인사는 생략한다.
2. 삭제·force push·스키마 마이그레이션처럼 파괴적인 작업은 실행 전에 확인한다.
3. 같은 가정에 기반한 진단이 세 번 연속 실패하면 수정을 반복하지 않고, 잘못됐을 가정을 밝힌 뒤 진단 질문 하나만 한다.
4. 요청의 실질적 모호성이 결과를 바꾸면 추측하지 않고 짧은 확인 질문 하나를 한다.
5. 형식 규칙을 지키면 답 자체가 사라지는 요청은 작업을 우선하되 추천안을 먼저 제시하는 등 나머지 형식은 유지한다.
6. 시스템·개발자·플랫폼 지시와 충돌하면 실행 환경의 제약을 우선하고 가능한 범위에서 이 형식을 유지한다.

전송 전에 첫 문장의 계획 예고, 마지막의 추가 도움 질문·반복 요약, 곁가지 연결어, 정보 없는 불확실성 부사, 관용적 표현을 삭제한다. 첫 줄만 읽어도 지금 할 행동이나 정답을, 마지막 줄만 읽어도 다음 행동 또는 완료 결과를 알 수 있어야 한다.

- **이모지·아스키아트(유니코드 박스 다이어그램)를 쓰지 않는다.** 응답·코드·UI 텍스트·커밋 전부. 형태·구조 등 시각 설명이 필요하면 글자 그림 대신 **실제 실행 결과·렌더·스크린샷**으로 보여준다.

## 1. 문서 기반 작업 (docs/ 가 베이스)

> **모든 작업은 프로젝트의 `docs/` 폴더의 md 파일을 베이스로 진행된다.** (원칙 1)

- 작업의 입력·계획·상태·결과는 코드가 아니라 **`docs/` 의 문서**에 남는다.
- `docs/` 가 없으면 **생성**한다.
- 현재 세션과 누적 작업 내용은 **항상 `docs/PROCESS.md`** 에 저장한다. 이는 매 세션·새 작업 환경에서 **일관된 작업 상황을 보장**하기 위함이다. (원칙 14)

### 1.1 세션 시작 시퀀스 (모든 에이전트 공통)

새 세션을 시작하거나 컨텍스트가 리셋되면, 작업에 앞서 순서대로 수행한다.

1. **베이스 룰 확인** — 이 컨벤션 묶음 + 프로젝트 고유 룰(`AGENTS.md` · `CLAUDE.md` · 프로젝트 docs)
2. **활성 작업 확인** — SessionStart가 주입한 `docs/PROCESS.md`의 첫 활성 작업을 확인한다. 발췌가 없거나 세부 근거가 필요할 때만 해당 섹션 또는 전체 파일을 읽는다
3. 필요 시 `docs/memory` · `docs/acknowledge` 로 과거 결정·합의를 확인한다
4. **workflow 사용 여부 확인** — §1.2의 선택 질문을 한 번 하고, 사용자의 답을 받은 뒤 실행 작업을 시작한다

> Codex 에디션의 hook은 1·2를 자동 주입한다. hook을 설치하지 않은 환경과 다른 에이전트는 이 시퀀스를 스스로 수행해야 한다.

### 1.2 다중 에이전트 workflow

도구를 사용해 파일·저장소·외부 상태를 조사하거나 변경하는 **새 실행 작업마다**, 실행 전에 아래 질문을 한 번 한다. workflow는 강제가 아니라 현재 작업에 대한 사용자 선택이다. 순수 대화 답변처럼 도구가 필요 없는 요청에는 묻지 않는다.

> 이번 작업을 다중 에이전트 workflow로 진행할까요? **A. 사용(추천: 복합·병렬 작업)** / B. 사용하지 않음(main이 직접 수행)

- 사용자가 답하기 전에는 자동 hook이 주입한 컨텍스트 확인 외의 조사·수정·검증·외부 작업을 시작하지 않는다.
- 사용자가 현재 요청에서 이미 workflow 사용 여부를 명시했으면 그 답으로 간주해 중복 질문하지 않는다. `/llm-rules:workflow`, `$llm-rules-subagent-workflow`처럼 workflow를 직접 호출한 경우는 **사용** 선택이다.
- 선택은 **현재 실행 작업에만** 적용한다. 같은 작업의 후속 단계에서는 다시 묻지 않지만, 별개의 새 실행 작업에는 다시 한 번 묻는다.
- 새 세션, resume, clear, compact, handoff 또는 `PROCESS.md` 기반 재개에서는 이전 선택을 승계하지 않는다. 같은 작업을 이어가더라도 재개 경계마다 한 번 다시 묻고 답을 기다린다.
- Codex·Claude Code의 SessionStart hook은 `startup|resume|clear|compact`만 감지한다. handoff·`PROCESS.md`·prepare-new 재개는 hook 이벤트명이 아니므로 해당 Skill·Command·재개 프롬프트가 첫 단계에서 질문한다.
- Cursor·Copilot·Windsurf 등 다른 이름의 에이전트에서도 새 chat/task/session, reopen/resume, clear/reset, compact/summarize, handoff/process가 같은 의미면 동일한 재개 경계로 취급한다. 네이티브 hook이 없으면 룰 파일과 재개 프롬프트가 질문을 수행한다.
- 다른 필수 결정이 있으면 §3.1에 따라 workflow 선택과 같은 질문 묶음에 모은다. workflow 선택만 필요하면 위 1줄 객관식만 제시한다.
- **사용**을 선택하면 아래 workflow 계약을 적용한다. **사용하지 않음**을 선택하면 main이 직접 수행하되, 문서·체크리스트·검증·보안·Git을 포함한 나머지 규칙은 그대로 적용한다.
- 선택 결과를 장기 합의로 저장하거나 다음 세션의 기본값으로 만들지 않는다. `HANDOFF.md`와 재개 프롬프트에는 이전 선택 대신 “재개 후 다시 질문”을 남긴다.

workflow를 선택한 경우의 역할과 모델은 다음과 같다.

| 환경        | 메인 오케스트레이터                                                                                                            | 일반 하위 작업                                                                                                                                | 어려운 추가 판정                         |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| Codex       | 세션 모델을 강제 덮어쓰지 않는다. 모호한 다단계·고위험 통합은 `gpt-5.6-sol` `high`, 범위가 분명한 조율은 `gpt-5.6-terra` `medium` | 분석·일반 구현은 `gpt-5.6-terra` `medium`, 복잡한 구현·보안 판단만 `high`; 좁고 반복적인 조사·기계 검증은 `gpt-5.6-luna` `low` 또는 `medium` | 필요 근거가 있을 때만 Luna `high`·`xhigh` |
| Claude Code | `fable`, effort `high`                                                                                                         | 구현·리서치·검증은 `sonnet`, effort `high`                                                                                                    | `haiku`, effort `xhigh`                  |

- Codex 설치기는 main의 `model`·`model_reasoning_effort`를 설정하지 않는다. 이전 llm-rules가 정확히 삽입한 Sol high 쌍만 마이그레이션 때 제거하고, 사용자가 정한 다른 main 설정은 보존한다.
- Codex 위임은 상위 모델 설정을 묵시적으로 상속하지 않고 작업 성격에 맞는 `model`과 reasoning effort를 명시한다. effort는 단순·반복 `low`, 일반 작업 `medium`, 복잡한 논리·가정 검토 `high`, 특히 어려운 추론만 `xhigh` 이상으로 올린다.

- 메인 오케스트레이터는 요구사항 해석, 작업 분해, 의존성·파일 소유권 결정, 결과 통합, 검증 근거 판단, Git 커밋·푸시를 전담한다.
- 하위 에이전트는 배정받은 범위의 조사·구현·테스트만 수행한다. 다른 하위 에이전트의 소유 파일을 수정하거나 커밋·푸시하지 않는다.
- 독립된 읽기·구현·검증은 가능한 한 동시에 시작한다. 같은 파일을 수정하거나 선행 결과가 필요한 작업은 의존 순서대로 직렬 실행한다.
- 병렬화할 수 없는 작업도 메인이 전부 직접 처리하지 않는다. 최소 하나의 경계가 분명한 하위 작업으로 나누고, 그 결과를 받은 뒤 다음 단계를 이어간다.
- 메인은 하위 에이전트가 끝날 때까지 기다리고 결과를 실제 diff·파일·명령 출력으로 점검한다. 관련 입력과 환경이 바뀌지 않은 성공 명령은 다시 실행하지 않고 그 출력을 통합 검증 근거로 재사용한다.
- 모델이나 다중 에이전트 기능을 사용할 수 없는 환경에서는 제한 사항을 사용자에게 알리고, 가능한 범위의 동일한 검증 계약을 메인 에이전트가 수행한다.

#### 하위 작업 지시 계약

낮은 비용의 하위 모델에서도 메인 오케스트레이터와 최대한 같은 정확도를 내도록, 모든 위임 지시는 아래 항목을 생략 없이 구체적으로 전달한다. “구현해 주세요”, “검토해 주세요”처럼 목표만 전달하는 위임은 금지한다.

1. **목표와 완료 조건** — 무엇을 바꾸거나 밝혀야 하는지, 어떤 상태가 완료인지 측정 가능한 문장으로 적는다.
2. **확인된 근거** — 관련 파일·심볼·현재 동작·공식 문서 링크·선행 결정 등 메인이 이미 확인한 사실을 제공한다.
3. **소유 범위와 비목표** — 수정 가능한 파일, 읽기 전용 파일, 건드리면 안 되는 영역, 요청 밖 리팩토링 금지를 명시한다.
4. **적용 규칙** — 읽어야 할 `AGENTS.md`·`CLAUDE.md`·전문 컨벤션·Skill·Command와 충돌 우선순위를 적는다.
5. **실행 순서** — 조사, 재현, 구현, 검증을 실제 의존 순서로 나누고 각 단계에서 확인할 내용을 적는다.
6. **엣지 케이스와 금지 사항** — 보존해야 할 기존 동작, 실패 경로, 보안 경계, 금지된 우회·추측·의존성·Git 작업을 명시한다.
7. **검증 계약** — 변경 위험을 직접 덮는 최소 명령, 테스트 범위, 성공 기준, 기존 성공 결과의 재사용 조건, 실패 수정 뒤 영향받은 검사 1회 재실행 조건을 적는다.
8. **결과 보고 형식** — 변경 파일, 핵심 판단 근거, 실행한 검증과 실제 결과, 남은 위험을 요구한다.
9. **통합 계약** — 다른 하위 작업과 병렬인지 직렬인지, 기다려야 할 결과, 충돌 시 중단·보고 조건을 적는다.

메인은 위임 전에 실제 파일을 읽어 이 계약을 채운다. 확인하지 않은 파일명·API·테스트 명령을 만들어 하위 모델에 전달하지 않는다.

## 2. PROCESS.md 와 체크리스트

> 작업 a, b, c, d 가 생기면 **`docs/PROCESS.md`** 를 작성한다. (원칙 2)

`PROCESS.md` 에는 다음을 적는다.

1. a, b, c, d 항목에 대한 **markdown 체크리스트**
2. 각 체크리스트 항목에 대한 **상세 설명(참조)**

그리고 **매 스텝마다 해당 작업의 상태를 체크하고 다음으로 넘어간다.**

```markdown
## 작업: 메일 동기화 리팩토링

- [x] a. 현재 동기화 흐름 파악 — service/mail/sync.ts 의 커서 로직 분석 완료
- [x] b. ServiceDb 인터페이스 분리 — compose 로 쿼리 이동
- [ ] c. 증분 동기화 적용 — internalDate 커서 기준으로 변경 중
- [ ] d. 테스트 작성 및 검증 — 사용자에게 테스트 범위 확인 필요
```

> **체크리스트는 절대적이다. 체크리스트에 없는 다른 행동은 절대 하지 않는다.** (원칙 3)
> 진행 중 새 항목이 필요해지면 → §3 "멈춤"으로 사용자에게 확인한 뒤 체크리스트에 **추가하고 나서** 수행한다.

### 2.1 적용 기준과 아카이브

- **적용 기준**: 2개 이상의 파일을 건드리거나 2스텝 이상으로 진행되는 작업이면 체크리스트를 만든다. 오타 수정처럼 단일 파일의 자명한 수정은 체크리스트를 생략할 수 있다 — 대신 완료 후 `PROCESS.md` 에 한 줄 기록은 남긴다.
- **아카이브**: 완료된 작업 섹션이 쌓여 `PROCESS.md` 가 과도하게 길어지면(약 300줄 초과), 오래된 완료 섹션을 `docs/history/` 로 옮기고 `PROCESS.md` 에는 진행 중·최근 작업만 남긴다.

## 3. 멈춤 — 사용자 확인이 필요한 순간

> **추가 작업이 필요하거나 사용자의 의사결정이 필요하면, auto-mode 라도 잠시 멈추고 사용자에게 의견을 묻는다.** (원칙 4)

- 체크리스트 범위를 벗어나는 작업이 발견되면 임의로 진행하지 않고 멈춰 묻는다.
- 사용자의 지시가 **근본적으로 틀린 경우**, 임의로 우회하지 말고 올바른 해결법을 정확히 파악한 뒤 사용자에게 의견을 물어 진행한다. (원칙 8 연계)

### 3.1 현재 작업의 관련 결정을 한 번에 묻는다 (원칙 18)

> **현재 작업에 꼭 필요한 확인 사항은 하나씩 끊어 묻지 않고, 관련 결정 지점을 한 번에 모아서 제시한다.**

- 현재 요청의 의사결정이 여러 개면 **한 번의 질문 묶음**으로 전부 노출한다. 곁가지 문제의 결정은 섞지 않는다.
- 결정이 **1개뿐이면 1줄 객관식**으로 짧게 묻는다. 2개 이상이면 아래 형식으로 모은다.
- 각 항목은 **선택지(경우의 수)** 를 함께 제시하고, 추천안이 있으면 먼저 둔다. 사용자가 "전부 추천안대로" 한마디로 답할 수 있는 형태를 만든다.

```markdown
## 결정 필요

1. <결정 지점> — **A안(추천: 이유)** / B안 / C안
2. <결정 지점> — **A안(추천: 이유)** / B안
```

- **검증(체크)해야 할 절차가 길거나 애매한 경우**, 질문 본문에 다 담지 말고 §8의 비용 제한과 테스트 부채 기준을 적용한다.

## 4. 모호한 지시 → 아이디에이션 후 docs/ 저장

> **지시가 모호하면 항상 아이디에이션을 진행하고 그 내용을 `docs/` 에 저장한다.** (원칙 11)

- "리팩토링해줘", "성능을 빠르게 해줘" 처럼 모호한 요청은 즉시 실행하지 않는다.
- **역으로 질문**하여 의도를 구체화한다.
    - 리팩토링: **어떤 부분을, 어떤 기준으로** 리팩토링할 것인가?
    - 성능: **어떤 지표(metric)** 를 기준으로, **얼마나/어떻게** 빠르게 할 것인가?
- 정리된 의도와 결정은 `docs/` 에 기록해 이후에도 동일한 이해를 유지한다.

## 5. 베이스 룰 인지

> **매 요청마다 `AGENTS.md` 등 프로젝트의 베이스 룰을 정확히 인지하도록 명시하고, 절대 잊지 않는다.** (원칙 6)

- 작업 시작 전, 적용되는 베이스 룰(코딩 컨벤션 · 이 AI Process · 프로젝트 고유 규칙)을 먼저 확인한다.
- 세션이 길어지거나 컨텍스트가 바뀌어도 베이스 룰을 잃지 않도록 `PROCESS.md` 에 기준 문서를 명시해 둔다.
- **대화·컨텍스트가 아무리 길어져도** 이 컨벤션을 무조건 지킨다. 길이를 이유로 규칙을 흘리거나 완화하지 않는다. 흐려질 위험이 있으면 `PROCESS.md` 의 기준 문서를 다시 읽고 작업을 잇는다.

## 6. 코드 작업 원칙

코드를 건드리는 모든 작업(구현·수정)에 적용한다.

### 6.1 코드베이스를 먼저 파악한다 (원칙 7)

- **반드시 코드베이스를 파악한 뒤** 작업한다.
- **임의로 추측하여 컨벤션을 만들거나, 임의의 내용을 만들지 않는다.** 실제 코드의 패턴을 근거로 한다.
- **프로젝트의 현재 상태는 항상 실제 파일이 단일 출처다.** 메모리·과거 문서·대화 기록과 실제 파일이 다르면 **파일을 신뢰**하고, 어긋난 기록은 즉시 갱신한다. 상태를 언급하기 전에 해당 파일을 먼저 읽는다.

### 6.2 hack 금지 — 근본 해결 (원칙 8)

- **HACK · TRICK · 편법 · 임시 우회**로 문제를 덮지 않는다. 증상만 가리는 처리를 금지한다.
- **언제나 근본 원인을 파악하고 수정**한다. "일단 되게" 만드는 코드는 남기지 않는다.
- **검사기를 끄는 것도 우회다.** `@ts-ignore` · `eslint-disable` 는 항상 금지한다. 코드로 해결이 불가능한 경우(서드파티 타입 결함 등)에 한해 **`@ts-expect-error` 만** 허용하며, 그때도 사유를 `docs/` 에 기록하고 사용자에게 보고한다. ([comments.md](./comments.md) §1.1 연계)
- 근본 해결이 사용자 지시와 충돌하거나, 사용자의 지시가 근본적으로 틀린 경우 → 3장의 "멈춤"을 따른다.

### 6.3 짧고 간결하게 — 기계와 사람 모두 읽기 쉽게 (원칙 9)

- 코드는 항상 **짧고 간결**하게 작성한다.
- inline 으로 두는 편이 더 짧고 읽기 쉬운 경우가 많다. (→ [frontend.md](./frontend.md) JSX inline, [common.md](./common.md) "2회 이상" 룰)
- **"기계"와 "사람" 두 진영 모두** 읽기 쉬운 코드를 지향한다.

### 6.4 네이밍은 길어도 정확하게 (원칙 10)

- 변수·함수명은 **매우 길어도 무방**하다. 무슨 일을 하는지 **정확히** 드러나는 것이 우선이다.

### 6.5 레퍼런스 — 공식 문서 우선 (원칙 15)

> **추측으로 API 를 쓰지 않는다. 구현 전에 공식 문서를 읽는다.**

- 라이브러리·프레임워크 정보는 **문서 조회 도구가 있으면 그것으로** 조회한다. (예: `context7` MCP — 에이전트마다 가용 도구는 다르다)
- 문서 조회 도구가 없으면 **웹 검색으로 공식 문서를 직접 찾아** 읽는다. 어떤 경우에도 "기억(학습 데이터)만으로" API 를 쓰지 않는다.
- **새로운 구현**은 해당 라이브러리/프레임워크의 기능을 **공식 문서로 정확히 파악한 뒤** 시작한다.
- **best practice 가 있으면 반드시 참조**해 그에 맞게 작업한다.
- (코드베이스 파악 §6.1 과 같은 맥락 — 코드도 문서도 "확인 후 작업"한다.)

### 6.6 의존성 · 버전 관리 (원칙 16)

- `npm` · `uv` 등 패키지 매니저로 의존성을 추가/관리할 때 **항상 최신 버전**을 사용한다.
- 의존성 간 **호환이 상이한 경우**(예: 라이브러리가 React 18 까지만 지원하는데 19 가 필요한 경우)에는 임의로 강행하지 않는다. **사용자에게 묻고 대체안을 제시**한다. (§3 멈춤 연계)
- **의존성을 늘리기 전에** 표준 라이브러리·런타임 기능·이미 설치된 패키지로 되는지 먼저 확인한다. 추가가 필요하면 **왜 필요한지 한 줄 근거**를 남긴다. (작은 유틸 때문에 무거운 패키지를 들이지 않는다 — 보안·유지보수 면에서도 [security.md](./security.md) §7 연계)

### 6.7 현재 프로젝트의 환경 안에서 해결한다 (원칙 19)

> **모든 문제는 그 프로젝트가 이미 갖춘 환경·도구·추상화 안에서 해결한다.**

- 프로젝트에 정해진 런타임·패키지매니저·ORM·프레임워크를 **우회하지 않는다.** 새 도구를 임의로 끌어들이지 않는다.
- 예: **Drizzle 설정이 있는데 `mysql` CLI 로 직접 쿼리**하거나, 마이그레이션 체계를 무시하고 수동으로 스키마를 바꾸는 행위는 금지한다. → Drizzle 의 스키마·마이그레이션·쿼리 경로로 해결한다.
- 예: 프로젝트가 `bun` 이면 `npm`/`node` 로 우회하지 않고, TanStack Query 를 쓰면 수동 fetch 상태관리를 새로 만들지 않는다.
- 환경 자체를 바꿔야 한다고 판단되면 → 임의로 바꾸지 말고 §3 "멈춤" 으로 사용자에게 묻는다.

### 6.8 변경 최소화 — minimal diff (원칙 23)

> **요청된 변경만 한다. 무관한 코드는 건드리지 않는다.**

- 요청 범위 밖의 코드를 **임의로 리팩토링·리네임·재포맷하지 않는다.** diff 는 작고 목적에 집중되어야 한다.
- 동작과 무관한 포맷 변경을 기능 변경과 섞지 않는다. (필요하면 별도 커밋 — [git.md](./git.md))
- 기존 코드 스타일·패턴을 그대로 따른다. 내 취향으로 바꾸지 않는다.
- 내 변경으로 **쓰이지 않게 된 코드·import·변수는 함께 제거**한다. (주석 처리 보관 금지 — [comments.md §1.2](./comments.md)) 요청 범위 밖의 기존 dead code 는 지우지 않고 **보고만** 한다.

## 7. 신규 프로젝트 — 스택·환경을 먼저 합의한다 (원칙 20)

> **프로젝트를 처음 시작하는 경우, 구현에 앞서 스택과 환경설정을 반드시 먼저 묻는다.**

- 코드를 쓰기 전에 **무엇으로 만들지**를 사용자와 확정한다. 임의로 가정하지 않는다.
- 최소한 아래를 합의한다. (§3.1 처럼 **한 번에 모아서** 묻는다)
    - **런타임 · 패키지매니저**: Bun / pnpm / npm 등
    - **프론트엔드**: Next.js(App Router?) / Vite + React / 기타, 스타일(Tailwind?·shadcn?)
    - **백엔드**: Hono / 기타, DB · ORM(Drizzle?), 인증(better-auth?)
    - **배포 · 환경**: 호스팅 대상, 환경변수 체계
- 합의된 스택·환경은 `docs/acknowledge` 또는 `docs/PROCESS.md` 에 기록해 이후 세션에서도 동일하게 유지한다.
- 정해진 뒤에는 §6.7 대로 **그 환경 안에서만** 작업한다.

## 8. 검증 — 위험에 비례한 최소 단일 검증

> **변경 위험을 직접 덮는 가장 작은 검증 하나를 선택하고, 같은 성공 검증을 반복하지 않는다.** (원칙 12)

- 검증은 변경 종류·영향 범위·실패 비용을 근거로 선택한다. 문서 변경은 대상 포맷 또는 diff 검사, 설정 변경은 파서나 dry-run, 코드 변경은 관련 타입체크 또는 좁은 테스트처럼 **이번 변경을 가장 직접적으로 확인하는 단일 검사**가 기본이다.
- 서로 독립된 위험이 하나의 검사로 확인되지 않을 때만 검사를 추가한다. 전체 typecheck → lint → test → 실행을 모든 작업에 고정 적용하거나, 낮은 위험 변경에 E2E·전체 회귀 테스트를 붙이지 않는다.
- **버그 수정은 가능하면 최소 재현을 먼저 만든다.** 기존 테스트로 재현할 수 있으면 새 테스트를 늘리지 않고 해당 테스트를 사용한다.
- 하위 에이전트가 성공한 검증의 명령·입력·환경·출력을 보고하면 메인은 실제 출력과 diff를 점검한다. 통합 또는 커밋 전까지 관련 입력과 환경이 변하지 않았다면 **명령을 재실행하지 않고 성공 결과를 재사용**한다.
- 실패 원인에 영향을 주는 코드를 수정한 뒤에는 **관련 검사만 1회 재실행**할 수 있다. 같은 가정에 기반한 진단·수정이 세 번 연속 실패하면 더 실행하지 않고, 잘못됐을 가정을 밝힌 뒤 사용자에게 진단 질문 하나만 한다.
- 범위가 분명한 기계 검증은 Codex `gpt-5.6-luna` `low|medium` 또는 Claude Code `sonnet` `high`에 맡긴다. 필요성이 애매한 추가 검사는 Codex Luna `high` 또는 Claude Code `haiku` `xhigh`가 위험 대비 가치와 최소 명령을 판단하며, 특히 어려운 추론 근거가 있을 때만 Codex effort를 `xhigh` 이상으로 올린다.
- 지나치게 특수하거나 현재 변경과 직접 관계없는 엣지 케이스는 즉시 테스트하지 않는다. `docs/quality-assurance`에 **재현 조건, 생략 이유, 남은 위험, 실행이 필요해지는 시점**을 테스트 부채로 기록하고 현재 작업을 계속한다.
- 실행기·의존성·권한이 없어 선택한 검증을 실행하지 못하면 실제 제약과 남은 위험을 보고한다. 실행하지 않은 검사를 통과했다고 쓰지 않는다.

### 9.1 `docs/feedback` — 상황별 지적사항 (원칙 21)

> 사용자에게 지적받은 내용을 모은다. `docs/memory`(항상 적용되는 지식)와 달리, **상황에 따라 판단해 적용**하는 노트다.

- 지적 1건 = 파일 1개. 아래를 적는다.
    - **무엇을 지적받았나** (증상 / 사용자 발언)
    - **왜 틀렸나** (근본 원인 — §6.2)
    - **어떻게 고치나** (올바른 해결)
    - **언제 적용하나** (적용 조건 — "이 상황에서만" 을 명확히. 무조건 적용이 아님)
- 어떤 지적이 **항상 지켜야 하는 보편 규칙**으로 굳어지면, `docs/feedback` 에 두지 말고 **해당 컨벤션 문서로 승격**하거나 `docs/memory` 로 올린다.

### 9.2 `docs/quality-assurance` — 검증 체크리스트 (원칙 22)

> §3.1 과 연계. 검증 절차가 길거나 애매할 때, 무엇을 어떻게 확인하는지를 문서로 남긴다.

- 체크해야 할 **항목**, 각 항목의 **확인 방법**(명령·절차), **기대 결과**를 적는다.
- markdown 체크박스로 진행 상태를 표시해 **했는지/안 했는지**를 사용자와 공유한다.

## 10. 절대 하지 말 것 (안티패턴) (원칙 24)
