# AI PROCESS — AI 작업 프로세스

> AI(Claude Code 등)가 이 저장소 및 이를 참조하는 프로젝트에서 작업할 때 **무조건 따라야 하는 운영 규칙**이다.
> Claude Code 환경에서는 이 문서가 **`CLAUDE.md` 에서 참조**되어 매 작업에 적용된다.
> [common.md](./common.md) · [comments.md](./comments.md) 등 코딩 컨벤션은 "코드가 어떻게 생겨야 하는가"를, 이 문서는 "AI 가 어떻게 일해야 하는가"를 규정한다.

---

## 0. 적용 방식

- Claude Code 사용 시, 프로젝트의 `CLAUDE.md` 가 이 문서를 참조하도록 명시한다.
- 이 규칙은 **선택이 아니라 절대**다. 모든 요청·세션에서 항상 우선한다.

---

## 1. 문서 기반 작업 (docs/ 가 베이스)

> **모든 작업은 프로젝트의 `docs/` 폴더의 md 파일을 베이스로 진행된다.** (원칙 1)

- 작업의 입력·계획·상태·결과는 코드가 아니라 **`docs/` 의 문서**에 남는다.
- `docs/` 가 없으면 **생성**한다.
- 현재 세션과 누적 작업 내용은 **항상 `docs/PROCESS.md`** 에 저장한다. 이는 매 세션·새 작업 환경에서 **일관된 작업 상황을 보장**하기 위함이다. (원칙 14)

---

## 2. PROCESS.md 와 체크리스트

> 작업 a, b, c, d 가 생기면 **`docs/PROCESS.md`** 를 작성한다. (원칙 2)

`PROCESS.md` 에는 다음을 적는다.

1. a, b, c, d 항목에 대한 **markdown 체크리스트**
2. 각 체크리스트 항목에 대한 **상세 설명(참조)**

그리고 **매 스텝마다 해당 작업의 상태를 체크하고 다음으로 넘어간다.**

```markdown
## 작업: 메일 동기화 리팩토링

- [x] a. 현재 동기화 흐름 파악 — service/mail/sync.ts 의 커서 로직 분석 완료
- [x] b. ServiceDb 인터페이스 분리 — compose 로 쿼리 이동
- [ ] c. 증분 동기화 적용 — internalDate 커서 기준으로 변경 중
- [ ] d. 테스트 작성 및 검증 — 사용자에게 테스트 범위 확인 필요
```

> **체크리스트는 절대적이다. 체크리스트에 없는 다른 행동은 절대 하지 않는다.** (원칙 3)

---

## 3. 멈춤 — 사용자 확인이 필요한 순간

> **추가 작업이 필요하거나 사용자의 의사결정이 필요하면, auto-mode 라도 잠시 멈추고 사용자에게 의견을 묻는다.** (원칙 4)

- 체크리스트 범위를 벗어나는 작업이 발견되면 임의로 진행하지 않고 멈춰 묻는다.
- 사용자의 지시가 **근본적으로 틀린 경우**, 임의로 우회하지 말고 올바른 해결법을 정확히 파악한 뒤 사용자에게 의견을 물어 진행한다. (원칙 8 연계)

---

## 4. 모호한 지시 → 아이디에이션 후 docs/ 저장

> **지시가 모호하면 항상 아이디에이션을 진행하고 그 내용을 `docs/` 에 저장한다.** (원칙 11)

- "리팩토링해줘", "성능을 빠르게 해줘" 처럼 모호한 요청은 즉시 실행하지 않는다.
- **역으로 질문**하여 의도를 구체화한다.
  - 리팩토링: **어떤 부분을, 어떤 기준으로** 리팩토링할 것인가?
  - 성능: **어떤 지표(metric)** 를 기준으로, **얼마나/어떻게** 빠르게 할 것인가?
- 정리된 의도와 결정은 `docs/` 에 기록해 이후에도 동일한 이해를 유지한다.

---

## 5. 베이스 룰 인지

> **매 요청마다 `CLAUDE.md` 등 프로젝트의 베이스 룰을 정확히 인지하도록 명시하고, 절대 잊지 않는다.** (원칙 6)

- 작업 시작 전, 적용되는 베이스 룰(코딩 컨벤션 · 이 AI Process · 프로젝트 고유 규칙)을 먼저 확인한다.
- 세션이 길어지거나 컨텍스트가 바뀌어도 베이스 룰을 잃지 않도록 `PROCESS.md` 에 기준 문서를 명시해 둔다.

---

## 6. 코드 작업 원칙

코드를 건드리는 모든 작업(구현·수정)에 적용한다.

### 6.1 코드베이스를 먼저 파악한다 (원칙 7)

- **반드시 코드베이스를 파악한 뒤** 작업한다.
- **임의로 추측하여 컨벤션을 만들거나, 임의의 내용을 만들지 않는다.** 실제 코드의 패턴을 근거로 한다.

### 6.2 hack 금지 — 근본 해결 (원칙 8)

- hack · 편법으로 문제를 해결하지 않는다.
- **언제나 근본 원인을 파악하고 수정**한다.
- 사용자의 지시가 근본적으로 틀린 경우 → 3장의 "멈춤"을 따른다.

### 6.3 짧고 간결하게 — 기계와 사람 모두 읽기 쉽게 (원칙 9)

- 코드는 항상 **짧고 간결**하게 작성한다.
- inline 으로 두는 편이 더 짧고 읽기 쉬운 경우가 많다. (→ [frontend.md](./frontend.md) JSX inline, [common.md](./common.md) "2회 이상" 룰)
- **"기계"와 "사람" 두 진영 모두** 읽기 쉬운 코드를 지향한다.

### 6.4 네이밍은 길어도 정확하게 (원칙 10)

- 변수·함수명은 **매우 길어도 무방**하다. 무슨 일을 하는지 **정확히** 드러나는 것이 우선이다.

### 6.5 레퍼런스 — 공식 문서 우선 (원칙 15)

> **추측으로 API 를 쓰지 않는다. 구현 전에 공식 문서를 읽는다.**

- 라이브러리·프레임워크 정보는 **`context7` MCP 로 조회**한다.
- `context7` 이 없으면 **웹에서 직접 공식 문서를 찾아** 읽는다.
- **새로운 구현**은 해당 라이브러리/프레임워크의 기능을 **공식 문서로 정확히 파악한 뒤** 시작한다.
- **best practice 가 있으면 반드시 참조**해 그에 맞게 작업한다.
- (코드베이스 파악 §6.1 과 같은 맥락 — 코드도 문서도 "확인 후 작업"한다.)

### 6.6 의존성 · 버전 관리 (원칙 16)

- `npm` · `uv` 등 패키지 매니저로 의존성을 추가/관리할 때 **항상 최신 버전**을 사용한다.
- 의존성 간 **호환이 상이한 경우**(예: 라이브러리가 React 18 까지만 지원하는데 19 가 필요한 경우)에는 임의로 강행하지 않는다. **사용자에게 묻고 대체안을 제시**한다. (§3 멈춤 연계)

---

## 7. 검증 — 항상 검증하고 다음 스텝으로

> **모든 task 는 항상 검증한 뒤 다음 스텝으로 넘어간다.** (원칙 12)

- 검증의 가장 좋은 수단은 **테스트 코드** 작성이다.
- 단, 테스트 작성 여부·범위는 **사용자에게 의견을 묻는다.**

---

## 8. 결과물 저장 · 분류

> **하나의 작업이 끝날 때마다** 모든 내용을 정확히 인지할 수 있도록 체계적으로 분류해 저장한다. (원칙 5)

| 경로 | 용도 |
|------|------|
| `docs/PROCESS.md` | 현재/누적 작업 상태와 체크리스트 (세션 간 연속성) |
| `docs/memory` | 장기 기억 — 결정·맥락·재사용 지식 |
| `docs/history` | 작업 이력 — 무엇을 했는지 시간순 기록 |
| `docs/bug` | 버그 기록 — 증상·원인·해결 |
| `docs/acknowledge` | 인지·확인 사항 — 사용자 결정·합의·전제 |
| `docs/utils` | 작업에 사용한 보조 툴·util·스크립트 (원칙 13) |

---

## 9. 요약 체크리스트

작업을 시작하기 전과 진행 중에 항상 아래를 만족하는지 확인한다.

- [ ] 베이스 룰(`CLAUDE.md` · 컨벤션 · 이 문서)을 인지했는가
- [ ] 작업이 `docs/PROCESS.md` 의 체크리스트로 정의되어 있는가
- [ ] 체크리스트 범위 밖의 행동을 하지 않는가
- [ ] 모호한 지시는 아이디에이션 후 `docs/` 에 정리했는가
- [ ] 코드 작업 전 코드베이스를 파악했는가 (추측·임의 컨벤션 금지)
- [ ] 공식 문서(`context7`/웹)를 읽고 best practice 를 따랐는가
- [ ] 의존성은 최신 버전인가, 충돌 시 사용자에게 확인했는가
- [ ] hack 없이 근본 원인을 해결하는가
- [ ] 코드가 짧고 간결하며, 네이밍이 정확한가
- [ ] 각 스텝을 검증(테스트 등)하고 넘어가는가
- [ ] 추가 작업·의사결정이 필요하면 멈추고 물었는가
- [ ] 작업 결과를 `docs/`(memory·history·bug·acknowledge·utils)에 분류 저장했는가
