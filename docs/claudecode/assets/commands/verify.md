ai-process.md 검증 규칙에 따라 코드 변경을 검증한다. 변경 위험과 실제 실행 경로에 필요한 가장 작은 검사를 선택하고, 이미 성공한 결과를 반복하지 않는다. 인자: `$ARGUMENTS` (검증 범위와 기존 성공 결과 힌트. 비어 있으면 변경분 전체).

## 1. 변경 범위 파악

- 미커밋 변경(스테이지/워킹) 목록 확인: !`git status --porcelain`
- 변경된 TS/JS 파일 목록 확인: !`git diff --name-only HEAD -- '*.ts' '*.tsx' '*.js' '*.jsx'`
- `$ARGUMENTS` 가 있으면 그 범위로 한정한다. 없으면 위 변경 파일 전체가 검증 대상이다.
- 변경된 TS/JS 가 없으면 검증할 코드가 없다고 담백하게 보고하고 종료한다.

## 2. 위험비례 검사 선택

- 타입 계약이 바뀌었으면 프로젝트의 `typecheck` 스크립트를 한 번 실행한다.
- 포맷·lint 대상이 바뀌었으면 변경 파일만 검사한다.
- 동작이 바뀌었으면 변경과 직접 관련된 테스트 또는 가장 짧은 실행 경로 하나를 선택한다.
- 문서·정적 설정처럼 더 작은 전용 파서가 있으면 전체 빌드 대신 그 파서를 사용한다.
- main이나 다른 작업자가 이미 성공한 같은 명령과 범위는 출력 근거를 재사용하고 실행하지 않는다.

## 3. 실패와 애매성 처리

- 실패는 파일·라인·기대값·실제값을 실제 출력대로 보고한다. 원인을 수정했다면 관련 검사만 한 번 다시 실행한다.
- 동일한 가정으로 세 번 실패하면 반복을 중단하고 잘못되었을 가능성이 있는 가정과 진단 질문 하나를 제시한다.
- 주 검증 뒤 사용자 영향이 있는 애매성이 남으면 `edge-case-verification-worker`에 최소 보조 검사 하나만 위임한다.
- 지나치게 특수하거나 작은 검사로 판정할 수 없으면 실행하지 않고 `docs/quality-assurance/` 테스트 부채로 재현 조건·생략 이유·위험·실행 시점을 전달한다.

## 4. 인터페이스 변경 확인

- props/시그니처/입력 타입 등 **컴포넌트·함수 인터페이스가 바뀌었는지** 변경 diff 를 확인한다.
- 바뀌었다면 대응 테스트(목 주입·prop 사용처)도 함께 고쳐야 함을 안내한다. 예: prop 제거 시 해당 prop 을 쓰는 테스트 수정, hook 목(`mockUseXxx.mockReturnValue(...)`)로 데이터 주입 전환.
- 임의로 테스트를 광범위하게 수정하지 않는다.

## 5. 보고

아래 형식으로 담백하게 보고한다(검증 안 된 "완벽/통과" 단언 금지 — 실제 실행 결과만):

- 위험도와 선택한 최소 검사
- 새로 실행한 검사와 재사용한 성공 결과
- 타입체크·테스트·실행 확인: 통과 / 실패 / 위험상 생략
- 인터페이스 변경 동반 수정 필요 여부 및 대상
- 남은 애매성 또는 QA 테스트 부채

검증을 통과하지 못하면 다음 스텝으로 넘어가지 말고, 무엇을 고쳐야 하는지 정리해 멈춘다.
