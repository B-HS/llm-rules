작업 요청: `$ARGUMENTS`

이 커맨드는 사용자가 다중 에이전트 진행을 선택했다는 뜻입니다. 메인 세션이 요구사항 해석, 분해, 통합, 최종 판정, Git 을 맡고 서브에이전트가 배정받은 범위를 수행합니다.

## 무엇을 위임할지

서브에이전트는 자기 컨텍스트를 새로 쌓아야 하므로 토큰과 시간이 듭니다. 아래에 해당하는 일만 위임하고 나머지는 메인이 직접 합니다.

- 서로 의존하지 않아 동시에 진행할 수 있는 조사·구현·검증
- 전체 테스트 실행이나 넓은 검색처럼 출력이 길어 메인 컨텍스트에 남길 필요가 없는 일
- 구현 과정을 보지 않은 눈이 필요한 리뷰

같은 파일을 고치거나 앞 단계 결과가 필요한 일은 순서대로 진행합니다. 한 파일 수정이나 짧은 순차 작업은 위임하지 않습니다.

## 서브에이전트

| 에이전트 | 쓰는 경우 |
| --- | --- |
| `research-worker` | 코드베이스·공식 문서의 사실 확인 (읽기 전용) |
| `implementation-worker` | 소유 파일이 분명한 구현·수정 |
| `verification-worker` | 타입체크·테스트·실행 확인 |
| `edge-case-verification-worker` | 주 검증 뒤에 남은 애매한 점 하나의 판정 |
| reviewer 7종 | 구현 뒤 해당 영역의 의미 리뷰 |

## 위임할 때 전달할 내용

서브에이전트는 이 대화를 보지 못합니다. 메인이 실제 파일을 읽어 확인한 내용으로 아래를 채웁니다. 확인하지 않은 파일명·API·명령은 적지 않습니다.

1. 목표와 완료 조건
2. 이미 확인한 사실과 배제한 가설: 관련 파일·심볼·현재 동작·선행 결정
3. 소유 범위: 수정할 수 있는 파일, 건드리지 않을 영역, 다른 작업자와의 순서
4. 검증: 실행할 최소 명령과 합격 기준, 다시 실행하지 않아도 되는 기존 성공 결과
5. 보고 형식: 변경 파일과 근거, 명령별 실제 결과, 미검증 사항과 남은 위험

## 통합

1. 서브에이전트가 끝나면 보고만 믿지 않고 실제 diff 와 검증 출력을 확인합니다. 입력과 환경이 같은 성공 명령은 다시 실행하지 않습니다.
2. 주 검증 뒤에도 사용자 영향이 있는 애매한 점이 남을 때만 `edge-case-verification-worker` 를 씁니다. 작은 검사로 판정할 수 없으면 `docs/quality-assurance/` 에 테스트 부채로 남깁니다.
3. `docs/PROCESS.md` 를 갱신하고, 메인이 논리 단위로 선별 스테이징해 커밋하고 push 합니다. 서브에이전트는 Git 을 다루지 않습니다.
4. 완료 결과, 변경 범위, 실제 검증 결과, 커밋과 푸시 상태, 남은 위험을 보고합니다.
