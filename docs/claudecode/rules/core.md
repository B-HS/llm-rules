# llm-rules 코어 (Claude Code)

모든 프로젝트에 적용하는 작업 방식과 코드 규칙의 요약이다. 이 파일은 `install-claude-code` 가 관리한다.

- 도메인별 상세 규칙과 예시는 `{{RULES_DIR}}/` 에 있고, 해당하는 파일을 읽거나 편집하면 자동으로 로드된다. 이 요약과 다르면 상세 규칙을 따른다.
- 반복 절차는 커맨드에 있다: `/llm-rules:process` · `save-docs` · `log-feedback` · `verify` · `audit-*` · `workflow`, 세션 인계는 `/prepare-new`.
- 응답은 한국어 존댓말로 간결하게 쓴다. 형식은 output style `llm-rules` 가 정한다.

## 우선순위

- 시스템·실행환경 지시, 이번 대화의 사용자 지시, 프로젝트 룰(그 레포의 `CLAUDE.md` · `AGENTS.md` · `docs/acknowledge`), 이 컨벤션, 기존 코드 패턴 순으로 따른다.
- 상위 지시 때문에 이 컨벤션과 다른 선택을 했으면 그 사실을 알린다. 사용자가 차이를 모른 채 결과를 받지 않게 하기 위해서다.
- 컨벤션이 다루지 않는 주제는 기존 코드 패턴, 프레임워크 공식 권장 순으로 따른다. 그래도 정해지지 않으면 묻고, 새 컨벤션을 만들어 내지 않는다.

## 작업 진행

- 요청받은 작업은 완료될 때까지 이어서 한다. 오류·타임아웃·빈 결과 같은 일반 장애물은 원인을 진단하고 가진 권한 안에서 해결한다. 남은 일을 나열하고 끝내거나 계속할지 되묻지 않는다.
- 확인 없이 진행하는 일: 파일 읽기와 검색, 요청 범위 안의 편집, 로컬 검증 실행, `docs/` 기록, 체크리스트 항목 추가, 일반 커밋과 푸시.
- 멈추고 묻는 일은 아래로 한정한다. 질문은 현재 작업에 필요한 것만 한 번에 모으고 선택지마다 추천안을 먼저 둔다. 결정이 하나면 한 줄 객관식으로 묻는다.
    - 결과를 바꾸는 모호성. "리팩토링해줘", "빠르게 해줘"처럼 대상·기준·지표가 없는 요청이 여기에 든다. 정리된 의도와 결정은 `docs/` 에 기록한다.
    - 요청 범위를 넓히는 작업이나 정책 결정
    - 삭제, 스키마 마이그레이션, 이력 재작성처럼 되돌리기 어려운 작업
    - 신규 프로젝트의 스택과 환경: 런타임·패키지매니저, 프론트엔드, 백엔드·DB·ORM·인증, 배포·환경변수 체계. 합의 내용은 `docs/acknowledge` 또는 `docs/PROCESS.md` 에 기록한다.
    - 의존성 간 호환 충돌. 대체안과 함께 묻는다.
    - 같은 가정에서 나온 진단·수정이 세 번 연속 실패한 경우. 틀렸을 가정을 밝히고 진단 질문 하나만 한다.
- 사용자의 지시가 기술적으로 틀렸다고 판단되면 조용히 우회하지 않는다. 올바른 해결법과 근거를 제시하고 의견을 묻는다.

## 문서 기록 (`docs/`)

- 2개 이상의 파일을 건드리거나 2스텝 이상인 작업은 시작할 때 `docs/PROCESS.md` 에 체크리스트를 만들고 스텝마다 상태를 갱신한다. `docs/` 가 없으면 만든다. 단일 파일의 자명한 수정은 완료 후 한 줄 기록만 남긴다.
- 체크리스트는 작업 범위의 기준이다. 요청 범위 안에서 완료에 필요한 항목이 새로 생기면 체크리스트에 추가하고 계속한다. 범위를 넓히는 항목은 위 기준에 따라 묻는다.
- 세션을 시작할 때 `docs/PROCESS.md` 에 진행 중인 작업이 있으면 그 상태에서 이어 간다. 프로젝트 상태는 실제 파일이 단일 출처이므로, 메모리나 과거 문서와 다르면 파일을 믿고 어긋난 기록을 고친다.
- 작업이 끝나면 결과를 분류해 저장한다.

| 경로 | 내용 |
| --- | --- |
| `docs/PROCESS.md` | 현재·누적 작업 상태와 체크리스트. 약 300줄을 넘으면 오래된 완료 섹션을 `docs/history/` 로 옮긴다 |
| `docs/memory` | 장기 결정·맥락·재사용 지식 |
| `docs/history` | 작업 이력 |
| `docs/bug` | 버그의 증상·원인·해결 |
| `docs/acknowledge` | 사용자 결정·합의·전제 |
| `docs/utils` | 작업에 쓴 보조 스크립트 |
| `docs/feedback` | 지적 1건당 파일 1개: 무엇을 지적받았나, 왜 틀렸나, 어떻게 고치나, 언제 적용하나. 항상 적용할 보편 규칙이 되면 컨벤션이나 `docs/memory` 로 올린다 |
| `docs/quality-assurance` | 검증 항목·방법·기대 결과의 체크박스, 테스트 부채 |

## 구현 원칙

- 코드베이스를 먼저 읽고 실제 패턴을 근거로 작업한다. 추측으로 컨벤션이나 내용을 만들지 않는다.
- 라이브러리·프레임워크 API 는 문서 조회 도구나 웹의 공식 문서로 확인한 뒤 쓴다. 학습 기억만으로 쓰면 버전 차이로 틀리기 쉽다. best practice 가 있으면 따른다.
- 증상을 가리는 임시 우회 대신 근본 원인을 고친다. `@ts-ignore` · `eslint-disable` 로 검사기를 끄는 것도 우회다. 코드로 해결할 수 없는 서드파티 타입 결함에 한해 `@ts-expect-error` 를 쓰고, 사유를 `docs/` 에 기록해 보고한다.
- 프로젝트가 이미 갖춘 런타임·패키지매니저·ORM·프레임워크 안에서 해결한다. Drizzle 이 있으면 raw SQL 이나 `mysql` CLI 를 쓰지 않고, `bun` 프로젝트에서 `npm` 을 쓰지 않는다. 환경 자체를 바꿔야 하면 묻는다.
- 요청된 변경만 한다. 무관한 리팩토링·리네임·재포맷을 섞지 않고 기존 스타일을 따른다. 내 변경으로 쓰이지 않게 된 코드와 import 는 함께 지우고, 요청 밖의 기존 dead code 는 보고만 한다.
- 의존성은 표준 라이브러리·런타임 기능·이미 설치된 패키지로 되는지 먼저 확인한다. 추가할 때는 최신 버전을 쓰고 필요한 이유를 한 줄로 남긴다.
- 코드는 짧고 간결하게, 이름은 길어도 정확하게 쓴다.

## 검증

- 변경 종류·영향 범위·실패 비용을 보고 이번 변경을 직접 확인하는 가장 작은 검사 하나를 고른다. 문서는 포맷이나 diff 검사, 설정은 파서나 dry-run, 코드는 관련 타입체크나 좁은 테스트가 기본이다. 한 검사로 덮이지 않는 독립된 위험이 있을 때만 검사를 추가한다.
- 입력과 환경이 같은 성공 결과는 다시 실행하지 않고 재사용한다. 실패 원인을 고친 뒤에는 관련 검사만 한 번 다시 실행한다.
- 버그 수정은 가능하면 최소 재현을 먼저 만든다. 기존 테스트로 재현되면 그 테스트를 쓴다.
- 현재 변경과 직접 관계없는 특수한 엣지 케이스는 지금 테스트하지 않는다. `docs/quality-assurance` 에 재현 조건, 생략 이유, 남은 위험, 실행이 필요해지는 시점을 테스트 부채로 기록한다.
- 실행하지 못한 검사는 제약과 남은 위험을 보고한다. 실행하지 않은 검사를 통과했다고 쓰지 않는다.

## 위임

- 작업 분해와 서브에이전트 위임은 사용자가 `/llm-rules:workflow` 를 호출하거나 요청에서 다중 에이전트 진행을 지시했을 때만 한다. 같은 작업을 넘긴다고 결과가 좋아지지 않고 토큰과 시간이 더 든다.
- 넓은 코드 탐색처럼 Claude Code 가 기본 제공하는 읽기 전용 탐색 위임은 필요할 때 써도 된다.
- 서브에이전트는 commit · push 를 하지 않는다. Git 은 메인 세션만 다룬다.

## Git

- 구현과 검증이 끝나면 별도 요청이나 승인을 기다리지 않고 커밋하고 현재 브랜치에 push 한다. 기본 브랜치에서도 같다. 사용자가 이번 작업에서 금지했거나, Git 저장소가 아니거나, remote·인증이 없으면 실행하지 않고 이유를 보고한다.
- 형식은 Conventional Commits v1.0.0 이다: `type(scope): 설명`. type 은 영어(`feat` · `fix` · `docs` · `style` · `refactor` · `perf` · `test` · `build` · `ci` · `chore` · `revert`), 설명은 마침표 없이 50자 안팎. 호환성이 깨지면 `!` 또는 대문자 `BREAKING CHANGE:` footer 를 쓴다.
- 언어와 스타일은 그 레포의 히스토리를 따른다. 커밋 전에 `git log --oneline -30` 을 읽고 맞춘다. 히스토리가 없으면 기본값(한국어 명사형 종결 `~추가` · `~수정`)을 쓴다. 히스토리가 Conventional Commits 가 아니면 그 형식을 따르고 차이를 알린다. 언어·스타일이 섞여 있으면 묻고, 결정을 `docs/acknowledge` 에 기록해 이후 계속 적용한다.
- 커밋 하나는 독립적으로 되돌릴 수 있는 논리 단위 하나다. 관련 구현·테스트·문서를 함께 두고, 동작하지 않는 중간 상태는 커밋하지 않는다.
- 한 번에 한 커밋분만 파일을 지정해 스테이징한다. `git add -A` · `git add .` 는 의도하지 않은 파일이 섞이므로 쓰지 않는다. `git status` 와 staged diff 를 확인한 뒤 커밋한다.
- author 는 사용자 단독이다. `Co-Authored-By` · `Generated with` · 세션 링크 같은 AI 서명과 트레일러를 넣지 않는다.
- force push(`--force` · `-f` · `--force-with-lease` · `--force-if-includes`)는 하지 않는다. 이력 재작성이 필요하면 사용자와 방향을 정한다.
- 브랜치는 사용자가 요청했거나 저장소 정책이 요구할 때만 `<type>/<요약>` kebab-case 로 만든다. 그 외에는 현재 브랜치에서 진행한다.
- 시크릿, 빌드 산출물(`dist/` · `node_modules/`), 키 파일은 커밋하지 않는다.

## 보안

- `.env` · `.env.*` · `secrets/` · 키 파일(`.pem` · `id_rsa`)은 읽지도 쓰지도 출력하지도 않는다. 새 환경변수는 `.env.example` 에 키 이름만 추가하고 값 입력은 사용자에게 안내한다.
- 코드·히스토리·로그에서 노출된 시크릿을 발견하면 바로 보고한다. 이력 재작성 같은 파괴적 조치는 임의로 하지 않는다.
- 입력 검증, Injection, XSS, 인증·인가 규칙은 코드 파일 작업 시 로드되는 `security.md` 를 따른다.

## 코드 규칙 요약

상세와 예시는 파일 작업 시 로드되는 규칙 문서에 있다. 새 파일을 처음 만들 때도 아래는 지킨다.

- TypeScript strict. 신규 프로젝트는 Bun, Python 은 `uv` 를 쓰고, 기존 프로젝트는 그 환경을 따른다.
- arrow function 만 쓴다. 클래스 메서드 축약과 불가피한 `function*` 만 예외다. 비동기는 `async` / `await`, 분기는 early return 으로 쓰고 삼항을 중첩하지 않는다.
- `const` 를 기본으로 하고 배열·객체는 비파괴 연산을 쓴다. 기본값은 `||` 대신 `??`.
- `any` 와 `enum` 을 쓰지 않는다. `unknown` 은 외부 경계에서만 받아 즉시 좁히고, enum 은 `as const` + union 으로 쓴다. `as` 로 검증을 대신하지 않는다.
- 추론되는 반환·변수 타입은 적지 않는다. 타입은 `z.infer` · `ReturnType` · `Parameters` · `Awaited` · `ComponentProps` · `Omit` / `Pick` · `$inferSelect` 로 원본에서 유도한다. `type` 을 기본으로 쓴다.
- 코드 주석을 쓰지 않는다. 공개 API 의 영어 JSDoc 만 예외이고, 설명은 `docs/` 에 남긴다.
- 의미 있는 리터럴은 UPPER_SNAKE_CASE 상수나 prop 으로 뺀다. 함수 공통화는 2회 이상 쓰일 때만 한다. named export 가 기본이다.
- 네이밍: 폴더·파일 kebab-case, 컴포넌트·타입 PascalCase, 변수·함수 camelCase, 상수 UPPER_SNAKE_CASE, Boolean `is` / `has` / `can` / `should`, 핸들러 `handle~`, Hook `use~`, HOF `with~`, Factory `create~`.
- 이모지와 아스키아트는 코드·UI·커밋·문서·응답 어디에도 쓰지 않는다.
- 프론트엔드: 변형 FSD(`app → pages → widgets → features → entities → shared`, 의존은 위에서 아래로만), barrel 없이 alias 로 파일 직접 import, 1파일 1 export, `FC<Props>`, 본문 순서 `useRef → useState → 함수·로직 → useEffect·custom hooks`. `useCallback` · `useMemo` 는 쓰지 않고 React Compiler 에 맡긴다. `useEffect` 는 외부 시스템 동기화에만 쓴다. 서버 상태는 TanStack Query(`queryOptions` 팩토리 + `QUERY_KEY`), 폼은 react-hook-form + `zodResolver`.
- 백엔드(Hono · Drizzle): Route(DTO 검증·에러 변환) → Service(도메인 로직) → `*ServiceDb`(compose 의 Drizzle 구현). Factory DI, `withErrorHandling` · `withAuth` HOF, `createAppError`, 응답 헬퍼, `getEnv()`.
- 데스크톱: 렌더러는 프론트엔드 규칙을 따르고, IPC 는 타입 계약, preload 노출은 최소로 한다.
