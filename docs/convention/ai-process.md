# AI PROCESS — AI 작업 프로세스

> AI(Claude Code 등)가 이 저장소 및 이를 참조하는 프로젝트에서 작업할 때 **무조건 따라야 하는 운영 규칙**이다.
> Claude Code 환경에서는 이 문서가 **`CLAUDE.md` 에서 참조**되어 매 작업에 적용된다.
> [common.md](./common.md) · [comments.md](./comments.md) 등 코딩 컨벤션은 "코드가 어떻게 생겨야 하는가"를, 이 문서는 "AI 가 어떻게 일해야 하는가"를 규정한다.

---

## 0. 적용 방식

- Claude Code 사용 시, 프로젝트의 `CLAUDE.md` 가 이 문서를 참조하도록 명시한다.
- **Claude 외 코딩 에이전트(Cursor · Copilot · Windsurf 등)** 는 이 문서가 자동 주입되지 않는다. 각 에이전트의 룰 파일(`.cursor/rules` · `AGENTS.md` 등)에서 이 컨벤션 묶음을 **명시적으로 로드/참조**하도록 설정한다.
- 이 규칙은 **선택이 아니라 절대**다. 모든 요청·세션에서 항상 우선한다.

### 0.1 커뮤니케이션 (원칙 17)

> **항상 간결하게, 존댓말로 답한다.**

- 모든 응답·문서·커뮤니케이션은 **한국어 + 존댓말**로 작성한다. ([common.md](./common.md) §1)
- **미사여구·과장·빈말을 넣지 않는다.** 결론과 근거만 짧게 전한다.
- 장황한 재설명·중복 요약을 피한다. 이미 합의된 사실을 다시 늘어놓지 않는다.
- **이모지·아스키아트(유니코드 박스 다이어그램)를 쓰지 않는다.** 응답·코드·UI 텍스트·커밋 전부. 형태·구조 등 시각 설명이 필요하면 글자 그림 대신 **실제 실행 결과·렌더·스크린샷**으로 보여준다.

## 1. 문서 기반 작업 (docs/ 가 베이스)

> **모든 작업은 프로젝트의 `docs/` 폴더의 md 파일을 베이스로 진행된다.** (원칙 1)

- 작업의 입력·계획·상태·결과는 코드가 아니라 **`docs/` 의 문서**에 남는다.
- `docs/` 가 없으면 **생성**한다.
- 현재 세션과 누적 작업 내용은 **항상 `docs/PROCESS.md`** 에 저장한다. 이는 매 세션·새 작업 환경에서 **일관된 작업 상황을 보장**하기 위함이다. (원칙 14)

### 1.1 세션 시작 시퀀스 (모든 에이전트 공통)

새 세션을 시작하거나 컨텍스트가 리셋되면, 작업에 앞서 순서대로 수행한다.

1. **베이스 룰 확인** — 이 컨벤션 묶음 + 프로젝트 고유 룰(`CLAUDE.md` · `AGENTS.md` · 프로젝트 docs)
2. **`docs/PROCESS.md` 읽기** — 진행 중 체크리스트·미완료 항목·기준 문서를 파악한다
3. 필요 시 `docs/memory` · `docs/acknowledge` 로 과거 결정·합의를 확인한다

> Claude Code 는 hook 이 1·2 를 자동 주입하지만, **다른 에이전트(opencode · Codex · pi 등)는 이 시퀀스를 스스로 수행해야 한다.**

## 2. PROCESS.md 와 체크리스트

> 작업 a, b, c, d 가 생기면 **`docs/PROCESS.md`** 를 작성한다. (원칙 2)

`PROCESS.md` 에는 다음을 적는다.

1. a, b, c, d 항목에 대한 **markdown 체크리스트**
2. 각 체크리스트 항목에 대한 **상세 설명(참조)**

그리고 **매 스텝마다 해당 작업의 상태를 체크하고 다음으로 넘어간다.**

```markdown
## 작업: 메일 동기화 리팩토링

- [x] a. 현재 동기화 흐름 파악 — service/mail/sync.ts 의 커서 로직 분석 완료
- [x] b. ServiceDb 인터페이스 분리 — compose 로 쿼리 이동
- [ ] c. 증분 동기화 적용 — internalDate 커서 기준으로 변경 중
- [ ] d. 테스트 작성 및 검증 — 사용자에게 테스트 범위 확인 필요
```

> **체크리스트는 절대적이다. 체크리스트에 없는 다른 행동은 절대 하지 않는다.** (원칙 3)
> 진행 중 새 항목이 필요해지면 → §3 "멈춤"으로 사용자에게 확인한 뒤 체크리스트에 **추가하고 나서** 수행한다.

### 2.1 적용 기준과 아카이브

- **적용 기준**: 2개 이상의 파일을 건드리거나 2스텝 이상으로 진행되는 작업이면 체크리스트를 만든다. 오타 수정처럼 단일 파일의 자명한 수정은 체크리스트를 생략할 수 있다 — 대신 완료 후 `PROCESS.md` 에 한 줄 기록은 남긴다.
- **아카이브**: 완료된 작업 섹션이 쌓여 `PROCESS.md` 가 과도하게 길어지면(약 300줄 초과), 오래된 완료 섹션을 `docs/history/` 로 옮기고 `PROCESS.md` 에는 진행 중·최근 작업만 남긴다.

## 3. 멈춤 — 사용자 확인이 필요한 순간

> **추가 작업이 필요하거나 사용자의 의사결정이 필요하면, auto-mode 라도 잠시 멈추고 사용자에게 의견을 묻는다.** (원칙 4)

- 체크리스트 범위를 벗어나는 작업이 발견되면 임의로 진행하지 않고 멈춰 묻는다.
- 사용자의 지시가 **근본적으로 틀린 경우**, 임의로 우회하지 말고 올바른 해결법을 정확히 파악한 뒤 사용자에게 의견을 물어 진행한다. (원칙 8 연계)

### 3.1 한 번에 모든 경우의 수를 묻는다 (원칙 18)

> **확인이 필요한 사항은 하나씩 끊어 묻지 않고, 가능한 모든 결정 지점을 한 번에 모아서 제시한다.**

- 의사결정이 여러 개면 **한 번의 질문 묶음**으로 전부 노출한다. (사용자가 왕복을 반복하지 않도록)
- 결정이 **1개뿐이면 1줄 객관식**으로 짧게 묻는다. 2개 이상이면 아래 형식으로 모은다.
- 각 항목은 **선택지(경우의 수)** 를 함께 제시하고, 추천안이 있으면 먼저 둔다. 사용자가 "전부 추천안대로" 한마디로 답할 수 있는 형태를 만든다.

```markdown
## 결정 필요
1. <결정 지점> — **A안(추천: 이유)** / B안 / C안
2. <결정 지점> — **A안(추천: 이유)** / B안
```

- **검증(체크)해야 할 절차가 길거나 애매한 경우**, 질문 본문에 다 담지 말고 `docs/quality-assurance` (→ §9 결과물 저장 · 분류)에 **체크 항목·확인 방법·체크리스트**를 적어 두고, 무엇을 어떻게 확인하면 되는지 그 문서로 안내한다. (했는지/안 했는지 체크박스로 표시)

## 4. 모호한 지시 → 아이디에이션 후 docs/ 저장

> **지시가 모호하면 항상 아이디에이션을 진행하고 그 내용을 `docs/` 에 저장한다.** (원칙 11)

- "리팩토링해줘", "성능을 빠르게 해줘" 처럼 모호한 요청은 즉시 실행하지 않는다.
- **역으로 질문**하여 의도를 구체화한다.
  - 리팩토링: **어떤 부분을, 어떤 기준으로** 리팩토링할 것인가?
  - 성능: **어떤 지표(metric)** 를 기준으로, **얼마나/어떻게** 빠르게 할 것인가?
- 정리된 의도와 결정은 `docs/` 에 기록해 이후에도 동일한 이해를 유지한다.

---

## 5. 베이스 룰 인지

> **매 요청마다 `CLAUDE.md` 등 프로젝트의 베이스 룰을 정확히 인지하도록 명시하고, 절대 잊지 않는다.** (원칙 6)

- 작업 시작 전, 적용되는 베이스 룰(코딩 컨벤션 · 이 AI Process · 프로젝트 고유 규칙)을 먼저 확인한다.
- 세션이 길어지거나 컨텍스트가 바뀌어도 베이스 룰을 잃지 않도록 `PROCESS.md` 에 기준 문서를 명시해 둔다.
- **대화·컨텍스트가 아무리 길어져도** 이 컨벤션을 무조건 지킨다. 길이를 이유로 규칙을 흘리거나 완화하지 않는다. 흐려질 위험이 있으면 `PROCESS.md` 의 기준 문서를 다시 읽고 작업을 잇는다.

## 6. 코드 작업 원칙

코드를 건드리는 모든 작업(구현·수정)에 적용한다.

### 6.1 코드베이스를 먼저 파악한다 (원칙 7)

- **반드시 코드베이스를 파악한 뒤** 작업한다.
- **임의로 추측하여 컨벤션을 만들거나, 임의의 내용을 만들지 않는다.** 실제 코드의 패턴을 근거로 한다.
- **프로젝트의 현재 상태는 항상 실제 파일이 단일 출처다.** 메모리·과거 문서·대화 기록과 실제 파일이 다르면 **파일을 신뢰**하고, 어긋난 기록은 즉시 갱신한다. 상태를 언급하기 전에 해당 파일을 먼저 읽는다.

### 6.2 hack 금지 — 근본 해결 (원칙 8)

- **HACK · TRICK · 편법 · 임시 우회**로 문제를 덮지 않는다. 증상만 가리는 처리를 금지한다.
- **언제나 근본 원인을 파악하고 수정**한다. "일단 되게" 만드는 코드는 남기지 않는다.
- **검사기를 끄는 것도 우회다.** `@ts-ignore` · `eslint-disable` 는 항상 금지한다. 코드로 해결이 불가능한 경우(서드파티 타입 결함 등)에 한해 **`@ts-expect-error` 만** 허용하며, 그때도 사유를 `docs/` 에 기록하고 사용자에게 보고한다. ([comments.md](./comments.md) §1.1 연계)
- 근본 해결이 사용자 지시와 충돌하거나, 사용자의 지시가 근본적으로 틀린 경우 → 3장의 "멈춤"을 따른다.

### 6.3 짧고 간결하게 — 기계와 사람 모두 읽기 쉽게 (원칙 9)

- 코드는 항상 **짧고 간결**하게 작성한다.
- inline 으로 두는 편이 더 짧고 읽기 쉬운 경우가 많다. (→ [frontend.md](./frontend.md) JSX inline, [common.md](./common.md) "2회 이상" 룰)
- **"기계"와 "사람" 두 진영 모두** 읽기 쉬운 코드를 지향한다.

### 6.4 네이밍은 길어도 정확하게 (원칙 10)

- 변수·함수명은 **매우 길어도 무방**하다. 무슨 일을 하는지 **정확히** 드러나는 것이 우선이다.

### 6.5 레퍼런스 — 공식 문서 우선 (원칙 15)

> **추측으로 API 를 쓰지 않는다. 구현 전에 공식 문서를 읽는다.**

- 라이브러리·프레임워크 정보는 **문서 조회 도구가 있으면 그것으로** 조회한다. (예: `context7` MCP — 에이전트마다 가용 도구는 다르다)
- 문서 조회 도구가 없으면 **웹 검색으로 공식 문서를 직접 찾아** 읽는다. 어떤 경우에도 "기억(학습 데이터)만으로" API 를 쓰지 않는다.
- **새로운 구현**은 해당 라이브러리/프레임워크의 기능을 **공식 문서로 정확히 파악한 뒤** 시작한다.
- **best practice 가 있으면 반드시 참조**해 그에 맞게 작업한다.
- (코드베이스 파악 §6.1 과 같은 맥락 — 코드도 문서도 "확인 후 작업"한다.)

### 6.6 의존성 · 버전 관리 (원칙 16)

- `npm` · `uv` 등 패키지 매니저로 의존성을 추가/관리할 때 **항상 최신 버전**을 사용한다.
- 의존성 간 **호환이 상이한 경우**(예: 라이브러리가 React 18 까지만 지원하는데 19 가 필요한 경우)에는 임의로 강행하지 않는다. **사용자에게 묻고 대체안을 제시**한다. (§3 멈춤 연계)
- **의존성을 늘리기 전에** 표준 라이브러리·런타임 기능·이미 설치된 패키지로 되는지 먼저 확인한다. 추가가 필요하면 **왜 필요한지 한 줄 근거**를 남긴다. (작은 유틸 때문에 무거운 패키지를 들이지 않는다 — 보안·유지보수 면에서도 [security.md](./security.md) §7 연계)

### 6.7 현재 프로젝트의 환경 안에서 해결한다 (원칙 19)

> **모든 문제는 그 프로젝트가 이미 갖춘 환경·도구·추상화 안에서 해결한다.**

- 프로젝트에 정해진 런타임·패키지매니저·ORM·프레임워크를 **우회하지 않는다.** 새 도구를 임의로 끌어들이지 않는다.
- 예: **Drizzle 설정이 있는데 `mysql` CLI 로 직접 쿼리**하거나, 마이그레이션 체계를 무시하고 수동으로 스키마를 바꾸는 행위는 금지한다. → Drizzle 의 스키마·마이그레이션·쿼리 경로로 해결한다.
- 예: 프로젝트가 `bun` 이면 `npm`/`node` 로 우회하지 않고, TanStack Query 를 쓰면 수동 fetch 상태관리를 새로 만들지 않는다.
- 환경 자체를 바꿔야 한다고 판단되면 → 임의로 바꾸지 말고 §3 "멈춤" 으로 사용자에게 묻는다.

### 6.8 변경 최소화 — minimal diff (원칙 23)

> **요청된 변경만 한다. 무관한 코드는 건드리지 않는다.**

- 요청 범위 밖의 코드를 **임의로 리팩토링·리네임·재포맷하지 않는다.** diff 는 작고 목적에 집중되어야 한다.
- 동작과 무관한 포맷 변경을 기능 변경과 섞지 않는다. (필요하면 별도 커밋 — [git.md](./git.md))
- 기존 코드 스타일·패턴을 그대로 따른다. 내 취향으로 바꾸지 않는다.
- 내 변경으로 **쓰이지 않게 된 코드·import·변수는 함께 제거**한다. (주석 처리 보관 금지 — [comments.md §1.2](./comments.md)) 요청 범위 밖의 기존 dead code 는 지우지 않고 **보고만** 한다.

## 7. 신규 프로젝트 — 스택·환경을 먼저 합의한다 (원칙 20)

> **프로젝트를 처음 시작하는 경우, 구현에 앞서 스택과 환경설정을 반드시 먼저 묻는다.**

- 코드를 쓰기 전에 **무엇으로 만들지**를 사용자와 확정한다. 임의로 가정하지 않는다.
- 최소한 아래를 합의한다. (§3.1 처럼 **한 번에 모아서** 묻는다)
  - **런타임 · 패키지매니저**: Bun / pnpm / npm 등
  - **프론트엔드**: Next.js(App Router?) / Vite + React / 기타, 스타일(Tailwind?·shadcn?)
  - **백엔드**: Hono / 기타, DB · ORM(Drizzle?), 인증(better-auth?)
  - **배포 · 환경**: 호스팅 대상, 환경변수 체계
- 합의된 스택·환경은 `docs/acknowledge` 또는 `docs/PROCESS.md` 에 기록해 이후 세션에서도 동일하게 유지한다.
- 정해진 뒤에는 §6.7 대로 **그 환경 안에서만** 작업한다.

## 8. 검증 — 항상 검증하고 다음 스텝으로

> **모든 task 는 항상 검증한 뒤 다음 스텝으로 넘어간다.** (원칙 12)

- 검증의 가장 좋은 수단은 **테스트 코드** 작성이다.
- 단, 테스트 작성 여부·범위는 **사용자에게 의견을 묻는다.**
- **버그 수정은 재현이 먼저다.** 가능하면 버그를 드러내는 **실패하는 테스트를 먼저 작성**해 재현한 뒤 고치고, 그 테스트가 통과하는지로 검증한다. (근본 해결 §6.2 와 같은 맥락)

### 8.1 최소 기계 검증 (모든 에이전트 공통)

코드를 변경한 작업은 **종료 전에 반드시** 아래 사다리를 순서대로 통과한다. (Claude Code 는 Stop hook 이 1을 자동 실행하지만, 다른 에이전트는 직접 실행해야 한다)

1. **타입체크** — `tsc --noEmit` (또는 프로젝트의 `typecheck` 스크립트)
2. **lint · format** — 프로젝트에 설정된 것 (`prettier --check` · eslint 등)
3. **기존 테스트** — 있는 테스트가 깨지지 않는지 (`bun test`)
4. **실행 확인** — 가능하면 실제 실행 경로(dev 서버·스크립트 실행)로 동작을 확인

- 프로젝트는 `package.json` 에 **`typecheck`·`test` 스크립트를 제공**한다 — 검증 사다리와 자동 훅이 결정적으로 동작하기 위한 전제다. `lint` 는 설정된 프로젝트에서만 요구된다.
- 실행기가 없는 환경(의존성 미설치 등)이면 **그 사실을 있는 그대로 보고**하고 넘어간다. 검증하지 않았으면서 "통과했다"고 보고하는 것을 금지한다.
- 검증 실패를 발견하면 **고치고 다시 검증**한 뒤에만 완료를 보고한다.

## 9. 결과물 저장 · 분류

> **하나의 작업이 끝날 때마다** 모든 내용을 정확히 인지할 수 있도록 체계적으로 분류해 저장한다. (원칙 5)

| 경로 | 용도 |
|------|------|
| `docs/PROCESS.md` | 현재/누적 작업 상태와 체크리스트 (세션 간 연속성) |
| `docs/memory` | 장기 기억 — 결정·맥락·재사용 지식 |
| `docs/history` | 작업 이력 — 무엇을 했는지 시간순 기록 |
| `docs/bug` | 버그 기록 — 증상·원인·해결 |
| `docs/acknowledge` | 인지·확인 사항 — 사용자 결정·합의·전제 |
| `docs/utils` | 작업에 사용한 보조 툴·util·스크립트 (원칙 13) |
| `docs/feedback` | 지적받은 내용 — **상황에 따라 적용**하는 교정 리포트 (왜 틀렸나·어떻게 고치나·언제 적용하나) (원칙 21) |
| `docs/quality-assurance` | 검증해야 할 사항·방법·체크리스트 — 했는지/안 했는지 체크박스로 추적 (원칙 22) |

### 9.1 `docs/feedback` — 상황별 지적사항 (원칙 21)

> 사용자에게 지적받은 내용을 모은다. `docs/memory`(항상 적용되는 지식)와 달리, **상황에 따라 판단해 적용**하는 노트다.

- 지적 1건 = 파일 1개. 아래를 적는다.
  - **무엇을 지적받았나** (증상 / 사용자 발언)
  - **왜 틀렸나** (근본 원인 — §6.2)
  - **어떻게 고치나** (올바른 해결)
  - **언제 적용하나** (적용 조건 — "이 상황에서만" 을 명확히. 무조건 적용이 아님)
- 어떤 지적이 **항상 지켜야 하는 보편 규칙**으로 굳어지면, `docs/feedback` 에 두지 말고 **해당 컨벤션 문서로 승격**하거나 `docs/memory` 로 올린다.

### 9.2 `docs/quality-assurance` — 검증 체크리스트 (원칙 22)

> §3.1 과 연계. 검증 절차가 길거나 애매할 때, 무엇을 어떻게 확인하는지를 문서로 남긴다.

- 체크해야 할 **항목**, 각 항목의 **확인 방법**(명령·절차), **기대 결과**를 적는다.
- markdown 체크박스로 진행 상태를 표시해 **했는지/안 했는지**를 사용자와 공유한다.

## 10. 절대 하지 말 것 (안티패턴) (원칙 24)

> 자주 어기는 금지 사항을 한곳에 모은다. 상세 근거는 각 문서를 본다.

- **추측으로 진행** — 코드베이스·공식 문서 확인 없이 가정. (§6.1 · §6.5)
- **HACK · TRICK · 임시 우회**로 증상만 덮기. (§6.2)
- **환경 우회** — 프로젝트 도구를 두고 딴 길로. 예: Drizzle 있는데 `mysql` 직접, `bun` 인데 `npm`. (§6.7)
- **요청 외 코드 수정** — 무관한 리팩토링·리네임·재포맷. (§6.8)
- **임의 의존성 추가** — 기존/표준으로 되는데 새 패키지부터. (§6.6)
- **`function` 키워드 / 1회성 조기 추상화 / 자명한 타입 명시.** ([common.md](./common.md) §3·§5)
- **`any` 사용 / `enum` 사용 / `as` 로 검증 대체.** ([common.md](./common.md) §5.4·§5.5)
- **매직넘버 하드코딩 / 이모지·아스키아트.** ([common.md](./common.md) §4.1·§1 · §0.1)
- **`@ts-ignore` · `eslint-disable` 로 검사기 끄기.** (§6.2 — `@ts-expect-error` 만 조건부 허용)
- **코드 주석 작성** (JSDoc 제외). ([comments.md](./comments.md))

- **FSD 역방향 import / 임의 전역 상태 라이브러리 도입** (zustand 는 frontend.md §6 의 실수요 조건에서만, 서버 상태의 store 반입 금지). ([fsd.md](./fsd.md) §2 · [frontend.md](./frontend.md) §6)

- **검증 없이 "통과했다" 보고.** (§8.1)
- **확인 사항을 하나씩 끊어 묻기** — 한 번에 모아서. (§3.1)
