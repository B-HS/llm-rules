# /prepare-new — 세션 핸드오프 준비

현재 세션을 종료하고 새 세션에서 **유실 없이** 작업을 이어가기 위한 준비 작업을 수행한다.
목표는 4가지다:

1. 현재 세션의 컨텍스트를 최대한 완벽하게 문서로 고정한다.
2. 사용자의 질문 의도, 답변 방향성, 의사결정 맥락까지 보존한다.
3. 새 세션에서 이 문서만 읽으면 현재 세션과 동일한 상태로 복원되게 한다.
4. 모든 문서는 **실제 코드와 정합성**을 가져야 한다. (문서가 코드를 못 따라가면 그 문서는 거짓말이다)

추가 컨텍스트(있는 경우): $ARGUMENTS

## Phase 0 — 세션 컨텍스트 전수 조사 (Inventory)

작업을 시작하기 전에, 현재 대화 전체를 처음부터 다시 훑고 다음을 목록화한다.
**요약하지 말고 목록화한다.** 요약은 유실의 시작이다.

- **목표**: 이 세션에서 사용자가 이루려던 최종 목표와 하위 목표
- **완료된 작업**: 실제로 코드/문서에 반영된 변경 (파일 경로 단위로)
- **진행 중 작업**: 시작했지만 끝나지 않은 것 — 어디까지 했고, 다음 한 줄이 무엇인지
- **미착수 작업**: 언급됐지만 시작 안 한 것
- **의사결정 기록 (매우 중요)**:
  - 채택된 결정 + **채택 이유**
  - 검토됐다가 **기각된 대안 + 기각 이유** (새 세션이 같은 삽질을 반복하지 않도록)
- **사용자의 방향성/선호**: 답변 스타일, 코드 스타일, 아키텍처 취향, 하지 말라고 한 것, 반복해서 지적한 것
- **미해결 질문**: 사용자가 물었는데 아직 답이 확정 안 된 것, 또는 Claude가 사용자에게 확인받아야 하는 것
- **암묵적 컨텍스트**: 대화 중 자연스럽게 형성됐지만 어디에도 안 적힌 전제들 (환경, 버전, 제약조건, 용어 정의)

이 목록은 이후 모든 Phase의 원천 데이터다. 대화가 길면 앞부분부터 순서대로 다시 읽어라.

## Phase 1 — 코드 ↔ 문서 정합성 검증

docs/를 수정하기 전에 먼저 현재 상태를 파악한다.

1. `git status`와 `git diff`(및 필요 시 `git log --oneline -20`)로 이번 세션의 실제 변경분을 확인한다.
2. `docs/` 전체 구조를 읽는다. 없으면 생성 대상으로 표시한다.
3. 문서의 모든 주장(파일 경로, 함수/API 시그니처, 설정 키, 코드 예시, 아키텍처 다이어그램, 실행 명령어)을 **실제 코드와 대조**한다.
4. 불일치 목록을 만든다: `[문서 위치] — [문서의 주장] — [코드의 실제] — [조치]`
5. 문서에는 있는데 코드에 없는 것(죽은 문서), 코드에는 있는데 문서에 없는 것(문서 공백) 둘 다 잡는다.

## Phase 2 — docs/ 최신화 및 고도화

Phase 0의 인벤토리와 Phase 1의 불일치 목록을 기반으로 docs/를 갱신한다.

**최신화 (정확성)**
- Phase 1의 모든 불일치를 해소한다. 문서를 코드에 맞춘다. (코드가 잘못된 경우는 문서에 `KNOWN ISSUE`로 명시하고 코드를 임의로 고치지 않는다 — 새 세션의 TODO로 넘긴다)
- 이번 세션의 변경 사항을 관련 문서에 모두 반영한다.

**고도화 (품질)**
- 문서 간 중복은 단일 출처(single source of truth)로 통합하고 나머지는 링크로 대체한다.
- 각 문서 상단에 `최종 갱신일`, `대응 코드 버전/커밋`을 명시한다.
- "왜"가 빠진 문서에 근거를 보강한다. (무엇을 하는지만 있고 왜 그렇게 했는지 없는 문서는 다음 세션에서 뒤집힌다)
- 새로 필요한 문서가 있으면 생성한다. 최소한 다음이 존재해야 한다:
  - `docs/ARCHITECTURE.md` — 전체 구조, 주요 컴포넌트, 데이터 흐름
  - `docs/acknowledge/` — 의사결정 기록 (ADR 스타일: 배경 / 결정 / 이유 / 기각된 대안. 결정 1건 = 파일 1개, ai-process §9 분류 체계와 동일 — 별도 DECISIONS.md 를 만들지 않는다)
  - `docs/HANDOFF.md` — Phase 3에서 작성 (세션 인수인계 전용, 항상 덮어쓰기)
- 그 외 기록도 ai-process §9 분류(`docs/memory`·`history`·`bug`·`feedback`·`quality-assurance`)를 따르고, 병렬 체계를 새로 만들지 않는다.

## Phase 3 — 세션 스냅샷: docs/HANDOFF.md 작성

새 세션의 **단일 진입점**이 될 문서를 작성한다. 이전 HANDOFF.md가 있으면 덮어쓴다.
다음 구조를 따른다:

```markdown
# HANDOFF — {날짜} 세션 스냅샷

## 1. 프로젝트 한 줄 정의
## 2. 현재 목표 (최종 목표 → 현재 마일스톤 → 직전 작업)
## 3. 완료 / 진행 중 / 미착수 (파일 경로 포함, 진행 중은 "다음 한 줄"까지)
## 4. 의사결정 요약 (채택 + 기각된 대안, 상세는 docs/acknowledge/ 링크)
## 5. 사용자 방향성 & 작업 규칙 (답변 스타일, 코드 스타일, 금지사항)
## 6. 미해결 질문 / 사용자 확인 필요 항목
## 7. 환경 & 전제 (버전, 실행 방법, 암묵적 제약)
## 8. 다음 세션 TODO (우선순위 순, 각 항목에 관련 파일 명시)
## 9. 문서 지도 (docs/ 각 파일이 뭘 다루는지 1줄씩)
```

작성 원칙:
- 대화를 안 본 사람이 이 문서만 읽고 이어서 작업할 수 있어야 한다.
- 모호한 표현 금지. "리팩토링 필요"(X) → "`src/auth/session.ts`의 `refresh()` 중복 호출 제거 필요 (Phase 0 결정 #3 참조)"(O)
- Phase 0 인벤토리의 항목이 하나라도 이 문서(또는 링크된 문서)에 없으면 유실이다.

## Phase 4 — 자체 검증 (유실 검사)

커밋하기 전에 스스로 검증한다:

- [ ] Phase 0 인벤토리의 모든 항목이 docs/ 어딘가에 존재하는가? (항목별로 대조)
- [ ] 문서의 모든 코드 참조(경로/시그니처/명령어)가 실제 코드와 일치하는가?
- [ ] HANDOFF.md만 읽고 "다음에 뭘 해야 하는지"가 즉시 명확한가?
- [ ] 기각된 대안과 그 이유가 기록되어 있는가?
- [ ] 사용자가 반복 강조한 선호/금지사항이 기록되어 있는가?

실패한 항목이 있으면 해당 Phase로 돌아가 보완한 뒤 다시 검증한다.
검증 통과 후 변경된 문서 목록을 사용자에게 보고한다. (git commit은 사용자가 요청한 경우에만)

## Phase 5 — 새 세션 재개용 프롬프트 출력

마지막으로, 사용자가 새 세션에 **그대로 복사-붙여넣기**할 프롬프트를 코드블록으로 출력한다.
다음 템플릿을 실제 내용으로 채워서 출력한다:

```
이전 세션에서 이어지는 작업이야. 아래 순서로 컨텍스트를 복원해:

1. docs/HANDOFF.md 를 정독해. 이게 이전 세션의 완전한 스냅샷이야.
2. HANDOFF.md의 "문서 지도"에 따라 docs/의 나머지 문서를 읽어.
3. HANDOFF.md 3번(진행 중 작업)에 언급된 코드 파일들을 실제로 열어서
   문서와 코드가 일치하는지 확인해. 불일치가 있으면 작업 시작 전에 보고해.

복원이 끝나면 다음을 나에게 요약해서 확인받아:
- 프로젝트 목표와 현재 마일스톤
- 직전 세션에서 한 일과 하다 만 일
- 내가 정한 작업 규칙/방향성 (5번 섹션)
- 네가 이해한 "지금 바로 할 다음 작업"

내 확인 없이는 코드를 수정하지 마.

## 작업 규칙 (이전 세션에서 확정됨)
{Phase 0에서 수집한 사용자 방향성/선호를 여기에 그대로 나열}

## 즉시 착수할 작업
{HANDOFF.md TODO 1순위를 구체적으로 — 파일 경로와 완료 조건 포함}

## 절대 하지 말 것
{기각된 대안 / 사용자가 금지한 것}
```

---

## 실행 원칙

- Phase는 반드시 0 → 5 순서로 진행하고, 각 Phase 완료 시 한 줄로 진행 상황을 보고한다.
- 이 커맨드는 **문서와 재개 프롬프트만** 산출한다. 애플리케이션 코드는 수정하지 않는다 (문서 내 코드 예시 수정은 예외).
- "대충 요약"은 이 커맨드의 실패 조건이다. 항목 단위 대조가 원칙이다.
- 대화가 매우 길어 전체를 정확히 복기하기 어렵다고 판단되면, 그 사실을 숨기지 말고 "복기 신뢰도가 낮은 구간"을 HANDOFF.md에 명시한다.
