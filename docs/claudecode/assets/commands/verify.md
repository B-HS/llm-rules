ai-process.md §7(검증) · §8(결과 저장) 에 따라 코드 변경을 검증한다. 모든 보고는 한국어·존댓말·간결하게(자축/이모지 금지). 인자: `$ARGUMENTS` (검증 범위 힌트 — 예: 도메인/파일/디렉터리. 비어 있으면 변경분 전체).

## 1. 변경 범위 파악

- 미커밋 변경(스테이지/워킹) 목록 확인: !`git status --porcelain`
- 변경된 TS/JS 파일 목록 확인: !`git diff --name-only HEAD -- '*.ts' '*.tsx' '*.js' '*.jsx'`
- `$ARGUMENTS` 가 있으면 그 범위로 한정한다. 없으면 위 변경 파일 전체가 검증 대상이다.
- 변경된 TS/JS 가 없으면 검증할 코드가 없다고 담백하게 보고하고 종료한다.

## 2. 타입체크 (tsc --noEmit)

- 먼저 `package.json` 의 scripts 를 확인해 `typecheck`(또는 `type-check`) 스크립트가 있으면 그것을 우선 사용한다.
  - 있으면: 프로젝트 패키지 매니저로 실행(`bun run typecheck` 등).
  - 없으면: `bunx tsc --noEmit` (Bun 런타임 기준). 프로젝트가 다른 매니저면 그에 맞춰 `tsc --noEmit` 을 호출한다.
- 에러가 나면 **파일·라인·메시지**를 그대로 정리한다. 추측으로 단정하지 말고 실제 출력 기준으로 보고한다.

## 3. 관련 테스트 실행

- 테스트 러너를 `package.json` / 설정에서 확인한다(vitest 또는 bun test).
- **변경과 관련된 테스트만** 실행한다(전체가 아니라 변경 파일에 대응하는 테스트).
  - vitest: `bunx vitest run <관련 경로>` (변경 파일에 대응하는 `*.test.ts`/`*.spec.ts`, 또는 변경 디렉터리).
  - bun test: `bun test <관련 경로>`.
  - 대응 테스트 파일을 못 찾으면 변경 파일을 import 하는 테스트를 `Grep` 으로 찾아 범위를 정한다.
- 실패가 나면 실패한 테스트명·원인을 정리한다.

## 4. 인터페이스 변경 시 테스트 동반 수정 안내

- props/시그니처/입력 타입 등 **컴포넌트·함수 인터페이스가 바뀌었는지** 변경 diff 를 확인한다.
- 바뀌었다면 대응 테스트(목 주입·prop 사용처)도 함께 고쳐야 함을 안내한다. 예: prop 제거 시 해당 prop 을 쓰는 테스트 수정, hook 목(`mockUseXxx.mockReturnValue(...)`)로 데이터 주입 전환.
- 임의로 테스트를 광범위하게 수정하지 않는다. 수정 범위가 모호하면 1줄 객관식으로 사용자에게 묻는다.

## 5. 보고

아래 형식으로 담백하게 보고한다(검증 안 된 "완벽/통과" 단언 금지 — 실제 실행 결과만):

- 타입체크: 통과 / 실패(에러 N건 — 파일·라인 요약)
- 테스트: 통과(N개) / 실패(실패 목록) / 대응 테스트 없음
- 인터페이스 변경 동반 수정 필요 여부 및 대상

검증을 통과하지 못하면 다음 스텝으로 넘어가지 말고, 무엇을 고쳐야 하는지 정리해 멈춘다.
