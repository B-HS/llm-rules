ai-process §9.1(`docs/feedback`, 원칙 21)에 따라, 이번 세션에서 사용자에게 받은 **지적·교정**을 `docs/feedback/` 에 기록한다.

`docs/feedback`은 `docs/memory`(항상 적용)와 달리 **상황에 따라 판단해 적용**하는 노트다. 무조건 적용 규칙으로 굳어지면 컨벤션 문서나 `docs/memory`로 승격한다.

## 1. 대상 지적 수집

- 인자가 있으면 그 지적을 대상으로 한다: `$ARGUMENTS`
- 인자가 없으면 **이번 세션 대화에서 사용자가 교정·반려·지적한 내용**을 추출한다. 예: "그거 아니야", "왜 ~했어", "~로 하지 마", 리뷰 반려, 재작업 요청 등.
- 지적이 여러 건이면 **1건 = 파일 1개**로 분리한다. 추측으로 만들지 말고, 실제 사용자 발언에 근거한 것만 기록한다.

## 2. 디렉토리·날짜 확인

- `docs/feedback/` 이 없으면 생성한다.
- 오늘 날짜: !`date +%F`
- 기존 파일 목록(중복·연관 확인): !`ls -1 docs/feedback/ 2>/dev/null || echo "(없음)"`

## 3. 파일 작성

파일명: `docs/feedback/YYYY-MM-DD-<짧은-kebab-슬러그>.md` (날짜 prefix + 지적 핵심을 kebab-case로).

각 파일에 ai-process §9.1 의 4요소를 반드시 적는다.

- **무엇을 지적받았나** — 증상 / 사용자 발언(가능한 한 원문 인용)
- **왜 틀렸나** — 근본 원인(§6.2, hack 아닌 root cause)
- **어떻게 고치나** — 올바른 해결
- **언제 적용하나** — 적용 조건. "이 상황에서만"을 명확히(무조건 적용이 아님)

추가로 맨 위에 메타(날짜, 관련 파일/PR/도메인)를 적는다. 본문은 한국어·존댓말·간결, 코드 주석은 본문이 아니므로 무관하나 자축 톤은 금지한다.

## 4. 컨벤션 승격 후보 표시

해당 지적이 **항상 지켜야 하는 보편 규칙**으로 보이면, 파일 하단에 다음을 명시한다.

```
## 승격 후보
- 대상: docs/convention/<문서>.md  또는  docs/memory
- 사유: (왜 상황 무관 보편 규칙인지)
```

승격은 이 커맨드가 직접 하지 않는다. 후보로만 표시하고, 실제 승격 여부는 사용자에게 1줄로 묻는다.

## 5. 보고

작성/수정한 파일 경로와 각 지적의 한 줄 요약, 승격 후보 유무를 담백하게 보고한다.
